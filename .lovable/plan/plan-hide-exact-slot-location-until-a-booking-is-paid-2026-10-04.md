# Plan: hide exact slot location until a booking is paid

The plan follows the current freeze on payments, refunds, pricing and the webhook, and makes no dependency changes. Nothing gets published. The frozen screens `slot.$id.tsx` and `reservations.tsx` need small, display-only edits, so they need your explicit OK.

| # | Change | Risk | Tests (in tests/security.test.ts) |
|---|---|---|---|
| 1 | New migration `drizzle/migrations/0003_location_privacy.sql`. Add generated columns `approx_lat` and `approx_lng`: the real coordinates plus a fixed per-slot offset of 150 to 300 m (derived from a hash of the slot id) and rounded to 3 decimals. Remove the `SELECT(lat,lng)` privilege on `slots` from `authenticated` and `anon`. Owners and admins keep exact coordinates through `get_slots_private`. Extend `get_slots_private` to also return `lat` and `lng`. In `queries.ts`, update `SLOT_COLUMNS` to select `approx_lat`/`approx_lng`, mapped to `lat`/`lng`. `withPrivate` replaces them with exact values when allowed. SlotMap, map sorting, distance and SlotForm (the owner's edit form, which merges exact values) work without other changes. | Med. Any `select('*')` or select on `lat`/`lng` breaks with a permission error. I'll search the code for these first. Existing data: none changed (10 slots get generated values). Realtime: the update payload carries the whole row to anyone with SELECT on the table. I'll check whether a revoked column leaks this way. If it does, realtime should only trigger a refetch, not carry data. | Non-owner reads `lat` directly: denied. Non-owner reads `approx_*`: the result is 150 to 300 m from the real spot. Owner, admin and paid driver get exact coordinates from `get_slots_private`. Unpaid driver does not. |
| 2 | Same migration. In `get_slots_private`, a driver qualifies only if the reservation is `upcoming`/`active`/`completed` AND `payment_expires_at IS NULL` AND `reservation_balance(r.id) <= 0` (a zero-price booking passes on its own). Owner and admin are unchanged. Right after payment, `verifyPayment` already marks the payment captured and clears the hold inside the same request, before the confirmation screen fetches again. So the address shows without waiting for the webhook. The confirmation screen re-fetches the slot query once payment succeeds (only the query call changes, no payment logic). | Low. Both existing reservations get checked against the new rule before the migration ships. An unpaid one will lose address access, which is intended. | Unpaid hold gets no address. A reservation that is paid in full gets the address. Cancelled or expired gets none. Owner and admin still get it. After verify succeeds and before the webhook arrives, the address is visible. |
| 3 | Report only. After publishing, recreate the `payments-maintenance` cron job with a URL of `https://www.usop.in/api/public/cron/payments`. The bearer token stays in the database (the `internal_tokens` hash / cron command), never in the repo. Rotate it at the same time. | Low | After publishing: check `cron.job_run_details` for success, check the endpoint's 200 response in the logs, confirm the dev URL is no longer called and that unpaid holds expire. |

Notes
1. Order of work: write the migration and test against the live data (2 reservations) → update `queries.ts` → make display-only fixes on screens → run the tests.
2. Why generated columns: they keep a single table, so realtime keeps working. A separate view or RPC would mean rewriting every query and losing realtime on the view.
3. On the reservations screen, the directions link uses `slot.lat`/`slot.lng`. That stays correct, because the slot passes through `withPrivate` and gets exact values for paid drivers. Unpaid drivers get the approximate point, which is acceptable.
4. Unsure: whether revoked columns are still sent in realtime update payloads. This gets checked first, and if they are, those payloads get stripped to ids only.
5. Unsure: whether `reservation_balance` handles zero-price and promo-covered bookings exactly. This gets checked against the function in migration 0002.
6. The new booking emails use `full_address` through `withPrivate`. Emails go out after payment, so the new rule leaves them unaffected.
7. Tests need the PG test role and are skipped in the sandbox, as before. Results will be reported honestly.
